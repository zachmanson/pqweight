# Coverage check: September 2026 mainnet sample

How much of real mainnet traffic do the current Migration templates cover, and which spend shapes make up the rest? Measured with `pqweight aggregate` as of the slice 4 ticket (`.scratch/pq-migration/issues/03-coverage-check.md`).

To reproduce:

```
python scripts/fetch-blocks.py <the three hashes> > sample.txt
pqweight aggregate --scheme ml-dsa-44 sample.txt
```

## What the check changed

The first run reported 2,046 inputs (8.1%) as unknown, the largest Unmapped bucket. They were 2,046 one-input transactions, each with a pay-to-anchor output and an `OP_RETURN OP_13` (Runes) output, each spending the previous transaction's anchor output: chains of rune mints.

Slice 1 had required the segwit marker before calling an empty spend pay-to-anchor. But Bitcoin Core rejects the marker when every witness is empty, so a transaction whose only inputs are anchor spends *must* be serialized in legacy form. The rule excluded the most common real shape. An empty scriptSig with no witness section is now pay-to-anchor too: a no-op, and the migrated transaction stays legacy unless another input gains a PQ witness.

This also means pay-to-anchor's 8.9% of inputs here is mostly rune activity, not Lightning fee bumping. Its share will swing with that activity, so it's not a stable baseline.

Later, the script-shape breakdown (see "Which template next") found 26 P2WPKH inputs filed as P2WSH non-multisig, because their DER signatures were 68 or 69 bytes and the template accepted only 70 to 73. Ticket 04 (`.scratch/pq-migration/issues/04-short-der-signatures.md`) changed every ECDSA template to accept the DER tag `0x30` and 9 to 73 bytes. The tables in this report are after that fix: P2WPKH gained exactly those 26 inputs (6,993 WU), and nothing else moved.

## The all-or-nothing migrated-total rule

394 transactions (2.7%) are partially mapped, carrying 402,984 WU (3.4% of baseline Weight). The rule leaves those out of every migrated total. (The decision below was made before ticket 04, on 420 transactions and 4.1%.)

**Recommendation: keep the rule.** 4.1% is small enough that the totals above describe most traffic, and the alternative (a partial migrated total that mixes migrated and unmigrated inputs) would be a number that corresponds to no real transaction. Revisit it if a future sample puts partially mapped weight well above 5%, or once the next template lands and shrinks it further.

**Decision (2026-09-22): keep the rule.**

## Which template next

**Recommendation: P2TR script-path, for leaves with one key and a signature check (slice 5).**

By Unmapped reason alone the sample was a tie: P2TR script-path and P2WSH non-multisig each held 2.1% of Input weight (before ticket 04 moved 26 misfiled inputs out of P2WSH non-multisig). So each bucket was broken down by script shape (below). Both turn out to be dominated by a single shape, so "which one is fewer shapes" doesn't decide it. What decides it is that the P2TR shape is a general structure, while the P2WSH shape is one protocol's script.

### Script-shape breakdown

Done as a one-off: the same three blocks re-fetched with `scripts/fetch-blocks.py`, bucket membership taken from `migrate()` itself (so the totals match the tables above exactly), then each input's leaf script or witnessScript disassembled and grouped. The scratch scripts aren't committed.

**P2TR script-path** (211 inputs, 150,956 WU):

| Leaf script shape | Inputs | % of inputs | Input weight | % of Input weight | WU per input |
|---|---|---|---|---|---|
| Inscription envelope: `<key> CHECKSIG OP_FALSE OP_IF "ord" ... OP_ENDIF` | 189 | 89.6% | 140,517 | 93.1% | 743 |
| One key behind a dropped tag: `<data> DROP <key> CHECKSIG` | 17 | 8.1% | 6,026 | 4.0% | 354 |
| One key, data on the stack: `<key> CHECKSIGVERIFY DROP ... DROP 1` | 2 | 0.9% | 2,356 | 1.6% | 1,178 |
| Two keys: `<key> CHECKSIGVERIFY <key> CHECKSIGVERIFY <push>` | 2 | 0.9% | 1,058 | 0.7% | 529 |
| Other data envelope (not `ord`), one key | 1 | 0.5% | 999 | 0.7% | 999 |

multi_a (`CHECKSIGADD`), timelocks and hashlocks did not occur. 209 of 211 inputs (99.3% of the bucket's weight) are the same structure: one 32-byte key, one `CHECKSIG`/`CHECKSIGVERIFY`, one 64 or 65-byte Schnorr signature on the stack, and everything else inert data. 195 of those 209 have a control block with no Merkle path (a single-leaf tree); the other 14 have one 32-byte path hash. The "leaf with no signature at all" case the first draft of this section worried about did not occur.

The weight is mostly the data, not the signature. Three large inscriptions (about 10 to 21 KB each) carry 46,946 WU, almost a third of the bucket. Inscription activity is also bursty: 160 of the 189 are in block 964185.

**P2WSH non-multisig** (323 inputs, 146,596 WU, before ticket 04):

| witnessScript shape | Inputs | % of inputs | Input weight | % of Input weight | WU per input |
|---|---|---|---|---|---|
| Two-key hashlock/CLTV contract (one exact script template) | 280 | 86.7% | 132,570 | 90.4% | 473 |
| Not P2WSH: P2WPKH with a 68 or 69-byte signature | 26 | 8.0% | 6,993 | 4.8% | 269 |
| Other contracts (timelocked multisig, hashlock variants) | 10 | 3.1% | 5,380 | 3.7% | 538 |
| Lightning anchor and `to_remote` | 7 | 2.2% | 1,653 | 1.1% | 236 |

The expectation that this bucket is mostly Lightning was wrong. Lightning is 7 inputs. The dominant shape is one exact script:

```
<key A> CHECKSIG NOTIF
    DUP HASH160 <20> EQUALVERIFY CHECKSIGVERIFY <locktime> CHECKLOCKTIMEVERIFY
ELSE
    <key B> CHECKSIGVERIFY SIZE 32 EQUALVERIFY HASH160 <20> EQUAL
ENDIF
```

278 of the 280 spends take the `ELSE` branch (two ECDSA signatures plus a 32-byte preimage); the other 2 take the timelocked refund branch. The 280 inputs have 280 different keys and show up in all three blocks (16, 144 and 120), so it's steady use, not one event. But they come from 170 transactions, one of which sweeps 87 of them into a single output. It is not a BOLT 3 script, and the sample alone doesn't identify which service uses it.

**The 26 "P2WPKH" rows were a misfiling (fixed by ticket 04).** Their witness is a DER signature and a 33-byte compressed key, and mempool.space confirms the spent outputs are P2WPKH. The P2WPKH template only accepts signatures of 70 to 73 bytes, but DER signatures can be shorter when `r` or `s` has leading zero bytes. They fall through to the P2WSH non-multisig catch-all, whose heuristic is "2 or more witness items" (see Assumptions). The P2PKH and P2SH-P2WPKH templates use the same 70 to 73 range, so they can misfile the same way, though it didn't happen in this sample.

### Why P2TR script-path

- **It's a structure, not a script.** A template for "a leaf whose only signature check is one key" covers inscriptions, tagged leaves and data-carrying leaves with one rule: swap the 32-byte key in the leaf for a PQ public key, swap the Schnorr signature for a PQ signature, keep every other byte. The P2WSH winner would be a template that recognizes one exact script. It covers 90% today but stops mattering as soon as that one service changes its script, and it teaches the codebase nothing it can reuse.
- **It's the direction PQ proposals take.** Proposals such as BIP-360 put PQ signatures inside tapscript-style leaves. A template for "PQ key and signature in a leaf" is the building block for modelling those, and multi_a (already out of scope, per `spec.md`) is the natural next step after it.
- **Same payoff.** Both buckets are 2.1% of Input weight, and each template would map about 90% of its bucket.

Things the slice 5 ticket has to settle:

- **The control block.** Its 32-byte internal key is an elliptic-curve key. Swapping it too, leaving it, or requiring a key-path-less (NUMS) internal key are different assumptions and change the weight. This belongs in ADR-0002's list of stated assumptions.
- **Push encoding.** A 1,312-byte ML-DSA-44 key needs `OP_PUSHDATA2`, so the leaf grows by more than the key-size difference. (That the push breaks the 520-byte element limit is already an ADR-0002 assumption.)
- **Data is migrated as is.** Inscription bytes stay the same size, so for inscription-heavy traffic the migrated-to-baseline ratio will be much lower than for plain payments. That's correct, not a bug, but the report of the next run should say so.
- **Volatility.** Like the rune mints behind pay-to-anchor, inscription volume swings. The share this template picks up in one sample shouldn't be treated as a stable baseline.

**Before slice 5, fix the short-signature misfiling.** Done in ticket 04: it moved the 26 inputs from Unmapped to P2WPKH.

**The new inputs grow much less than payments do.** The P2TR script-path single-key inputs go from 149,898 WU to 904,300 WU at ML-DSA-44 (6.0×), against 14.4× for P2WPKH and 17.0× for P2TR key-path. **Contracts grow like payments, not like inscriptions.** The P2WSH contract inputs go from 139,603 WU to 2,294,094 WU at ML-DSA-44 (16.4×), close to P2WPKH (14.4×): the hashlock contract carries two keys and two signatures and little else. The 12 P2SH-P2WSH ones grow less (10.4×): their 35-byte redeem-script scriptSig stays as it is, and 3 of them are spent with one of their two signatures empty.

**This answers the "one protocol's script" objection** in "Why P2TR script-path". The objection was against a template that recognizes the one hashlock/CLTV script. Weight only depends on which bytes are keys and signatures, so the template doesn't recognize any script. It finds keys and signatures by shape and covers the Lightning anchors, CSV-delayed two-key scripts, contracts with a multisig inside and the P2SH-P2WSH key-hash script with the same rule. If the unidentified service changes its script, its spends stay mapped.

Two details the shape breakdown didn't show, found while grilling the ticket:

- **A preimage can look like a signature.** 2 of the 280 hashlock claims have a random 32-byte preimage that starts with `0x30`, the DER tag. The loose check the fixed-layout templates use (tag plus 9 to 73 bytes) would swap it as a signature, so this template parses the whole DER structure.
- **Keys aren't always next to their `CHECKSIG`.** 5 inputs use `<K1> SWAP <K2> CHECKSIG …`, and contracts with a multisig inside list their keys before the threshold. So every key-shaped push counts, wherever it sits. A key in a branch the spend doesn't take still grows, because the whole script is in the witness.

The 280 hashlock contract inputs are still one service's traffic, from 170 transactions, and one of those sweeps 87 of them. Like the inscriptions behind slice 5, their share will differ in another sample.

## After slice 7: Key exposure (2026-09-23)

Ticket 07 (`.scratch/pq-migration/issues/07-key-exposure.md`) tags every input with its **Key exposure**: where its public key sat before the spend, as seen from the spending side. `aggregate` now groups inputs by tag and reports each group's **Added weight** (migrated minus baseline Input weight). The question: if only the coins whose keys are already on-chain migrate first, as BIP-360 proposes for P2TR, how much block space does that cost next to migrating everything?

**Migrating only the exposed keys adds about 2 blocks of space to these 3 blocks, instead of about 22.** At ML-DSA-44 the three blocks go from 11,978,184 WU to about 20.1 million (5.0 blocks' worth) if only Exposed in output inputs migrate, and to 98.5 million (24.6) if everything does. The Exposed in output inputs are the P2TR key-path (2,015) and P2TR script-path single-key (209) spends. They are 8.7% of today's Input weight and 9.4% of the Added weight, because as a group they grow slightly faster than the rest (14.3× vs 13.9×). Two effects nearly cancel: P2TR key-path grows the most of any type (17.0×), because a lone 64-byte Schnorr signature is the smallest spend today, while inscription data holds the script-path inputs to 6.0×.

This is exact, not an estimate, because outputs and transaction overhead don't change under any template. The one exception, the 2-byte segwit marker and flag a legacy-only transaction gains, can't hit this row: every Exposed in output spend is already segwit.

**It's a lower bound on what a Long-exposure attack could reach.** A Hashed until spend key is public too if its address was spent from before, and the spending side can't show that. Some of the 90.6% belongs to exposed keys, and this tool can't say how much.

Two notes:

- **P2PK and bare multisig** are now recognized as their own Unmapped reasons (both Exposed in output) instead of "legacy other". The sample has none, so the table doesn't change. They're recognized so the tag is right when they do show up: a mainnet P2PK spend (block 170) and a bare multisig spend (block 330001) are now fixtures.
- **The P2TR share is bursty.** 189 of the 209 script-path inputs are inscriptions, 160 of them in one block. Another sample will show a different Exposed in output share.

## Assumptions

Unmapped reasons are recognized from the spending side only, so they are heuristics, not proofs:

- **P2TR script-path**: after removing any annex, at least 2 witness items remain, and the last is 33 + 32k bytes with a first byte of `0xc0` or `0xc1`. A P2WSH spend whose last item happens to look like that would be misfiled. Since slice 5, spends that also pass the single-key leaf rule are mapped instead; the reason covers the rest.
- **P2WSH non-multisig**: any other empty-scriptSig spend with 2 or more witness items that no template matched. Since slice 6, spends whose script has a signature check and a key are mapped as P2WSH contract instead; the reason covers the rest (a truncated push, no signature check, no key).
- **P2SH-wrapped segwit non-multisig**: a `0014` or `0020` redeem-script push whose witness matched no template.
- **P2PK**: an empty witness and a scriptSig of exactly one push that parses as a strict DER signature. A P2SH spend whose redeem script is itself a single DER-shaped push would be misfiled.
- **Bare multisig**: an empty witness and a scriptSig of `OP_0` followed only by strict DER signatures, with no redeem script after them. `OP_0 <sig>` counts as bare 1-of-n multisig, not P2PK.
- **Key exposure** follows from the Baseline spend type or Unmapped reason alone (ticket 07, decision 2). P2TR script-path counts as Exposed in output: the output key is the internal key tweaked, so breaking it opens the key path whatever the leaves say.
- **P2WSH and P2SH-P2WSH contract** (a mapped type, but its template relies on a heuristic of the same kind): every key-shaped push (33 bytes starting `02`/`03`, or 65 bytes starting `04`), in the script or on the stack, is a public key, and every stack item with a consistent DER structure is a signature. A 33-byte data item starting `02`/`03` would be swapped as a key.
- **Pay-to-anchor**: any input with an empty scriptSig and an empty or absent witness. From the spending side this also covers other keyless outputs such as a bare `OP_TRUE`. They all have no signature, so all migrate as a no-op.

Plus every assumption the Migration templates already state (ADR-0002).
